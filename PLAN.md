# Iteron — plan

Iteron is a Blender add-on that generates 3D fractals (Mandelbulbs, Mandelboxes, Menger sponges, kaleidoscopic IFS,
quaternion Julias, …) as **real Blender objects**. You add one from `Shift+A`, shape it from one sidebar tab, and it
renders in Cycles and EEVEE, exports with Blender's own exporters, and takes modifiers, materials and keyframes like
any other mesh.

This document is the plan: how it looks, how it works, what is built first, and what comes from the two sample
sources (`sample_source/blender-addon-template` and `sample_source/Fractalchemy`).

> **Status: Phases 0 – 2 are implemented.** §9 records the measured answers, what changed from the design below,
> and what could not be verified here. Phase 3 (the live ray-marched preview) is next.

**Decisions** (reasoning in the sections that follow; your answers to the first round of questions are recorded in §12):

1. **One home in the UI.** Everything lives in a single **Iteron** tab in the 3D Viewport sidebar (`N`), plus one
   entry in the `Shift+A` Add menu. There are no floating windows, no custom editors, no pop-up dialogs and no
   panels in the Properties editor. Sections fold away and advanced ones start closed.
2. **The fractal is a normal mesh object** that carries its formula and parameters (`object.iteron`). The mesh is
   rebuilt from those parameters: live at preview resolution while you tweak, and on request at final resolution.
   Because it is a plain mesh, Blender's undo, `.blend` saving, keyframes, drivers, modifiers, materials, renderers
   and exporters all work without Iteron re-implementing any of them.
3. **Each formula is defined once**, as a short Python function written against a small vector vocabulary. That one
   definition drives the generated Blender properties, the sidebar widgets, the GPU shader (GLSL produced by
   tracing the function), the numpy CPU fallback, the presets and the tooltips.
4. **The GPU does the heavy sampling** through Blender's own `gpu` module: an offscreen float target and a generated
   shader, so the same code runs on OpenGL, Metal and Vulkan. A numpy path covers background mode and machines where
   the GPU path fails.
5. **Meshing is Fractalchemy's surface nets**, ported to numpy only (Blender bundles numpy but not scipy). It is
   watertight by construction and emits **quads**, which suit Blender better than triangles.
6. **Blender 4.2 LTS and newer**, developed and primarily tested on **5.x** (the current release). It is packaged as a
   Blender **Extension** (`blender_manifest.toml`), pure Python with no extra wheels, MIT licensed, and **distributed
   as a zip on GitHub releases**.
7. **Phase 1 is a small, complete loop**: add → tweak live → build final → render/export, with 8 distance-estimator
   formulas. **Output is meshes only** until the phases that add other types. Later phases build on the same core, in
   order: the live ray-marched viewport preview, flames and IFS point clouds, then Fractalchemy and Fragmentarium
   file import (§7).
8. **Iteron opens Fractalchemy's files**:
   * `.fa` flames and `.fa3d` 3D scenes, with the flame work (Phase 4);
   * `.fafrag` / `.frag` fragments (Phase 5).
9. **Branding lives in `branding/`** and is generated by a script. The add-on's icons are copied from there at build
   time, so there is one source for the artwork (§1.2, §3).

## 1. What the user sees

### 1.1 Installing and launching

* **Install**: download `iteron-x.y.z.zip` from the GitHub releases page. In Blender, choose *Edit ▸ Preferences ▸ Get
  Extensions ▸ ▾ ▸ Install from Disk…* and pick the zip, or drag it onto Blender. Enable it once; it stays enabled.
* **Launch** — three entry points, all leading to the same sidebar tab:
  1. **`Shift+A ▸ Iteron Fractal ▸`** a submenu grouped by family (*Bulbs*, *Boxes*, *Sponges & Cubes*, *Kaleidoscopic
     IFS*, *Quaternion*). Picking one adds the object at the 3D cursor, selects it and builds the preview.
  2. **The `Iteron` tab** in the viewport sidebar (`N`). With no Iteron object active it shows the quick-start (formula
     picker + *Add Fractal*); with one active it shows that fractal's controls.
  3. **`F3` search**: every operator has a clear name (*Iteron: Add Fractal*, *Iteron: Build Final Mesh*, *Iteron:
     Apply as Plain Mesh*), so Blender's search finds them and right-click ▸ *Add to Quick Favorites* works.
  4. **`File ▸ Import ▸ Fractalchemy (.fa, .fa3d, .fafrag, .frag)`** (Phases 4–5), through Blender's own file browser.
     The quick-start also has an *Open Fractalchemy File…* button.
* No default hotkeys are registered, so Iteron never clashes with the user's keymap.
* **Preferences** (the add-on's entry in Preferences) hold what is set once: the compute device (*Auto / GPU / CPU*),
  the default preview and final resolutions, a memory limit, the live-update delay, and the default for *Live
  Preview*.

The sections, with advanced ones closed by default:

| Section | Contents |
|---|---|
| **Header** | Object name · **Live** toggle (rebuild the preview as parameters change) · **Rebuild** · a progress bar while a job runs (`layout.progress`) and otherwise a status line: *Preview 96³ / Final 384³ · face count · build time*, or *Stale* when parameters changed since the last build. |
| **Shape** | The formula's parameters, grouped as the formula declares them. Every escape-time formula also gets the shared *Julia* sub-section. All widgets come from the schema, so nothing is hand-laid per formula. |
| **Region** *(closed)* | *Auto-fit* (a coarse pass shrinks the box to the fractal) or a manual centre and size — for meshing a detail at high resolution. |
| **Mesh** *(closed)* | *Preview resolution* (used live), *Final resolution* + **Build Final**, with a memory estimate and an optional *Cancel*. Also *Surface offset* (in voxels; 0.5 closes most estimators), *Normals* (*Smooth* / *Field gradient*), and **Apply as Plain Mesh**, which freezes the object and removes the Iteron settings. |
| **Color** *(closed)* | *Mode* (*Orbit trap*, *Iterations*, *Radius*, *Solid*) and Blender's own **colour-ramp widget** (`template_color_ramp`), drawn from the object's Iteron material. Editing it here or in the Shader Editor is the same thing. |

Blender doesn't allow custom colours or styling, so the clean look comes from structure:

* **Progressive disclosure:** three things are visible at first glance (formula, preset, shape).
* **`use_property_split` alignment** throughout.
* **Checkboxes in sub-section headers** (Julia), so an option takes no room until it's on.
* **One status line** instead of pop-up reports.
* **Errors shown inline:** a warning icon and one line of text in the header, never a modal.

### 1.3 Workflows

**A — add and shape (Phase 1)**
1. Run `Shift+A ▸ Iteron Fractal ▸ Mandelbulb`. The object appears at the cursor with its default material and a
   preview mesh about half a second later.
2. Drag *Power*. With *Live* on, each change schedules a preview rebuild after a short pause. A newer change always
   supersedes an older pending build, so the viewport never shows a stale result arriving late.
3. Pick a preset, try *Julia*, and adjust the colour ramp. Every edit is a normal Blender undo step. After an undo, Iteron
   notices that the mesh no longer matches the parameters and rebuilds it.

**B — final mesh, render, export (Phase 1)**
1. *Mesh ▸ Final resolution 384 ▸ Build Final*. Progress shows in the header and the status bar; `Esc` or *Cancel*
   stops it, and the UI stays responsive throughout.
2. Render with F12 in Cycles or EEVEE. To export, use *File ▸ Export ▸ glTF / OBJ / STL / PLY / USD* (Blender's
   exporters, including vertex colours).
3. Optionally add Decimate / Smooth / Subdivision modifiers. Rebuilds replace the mesh data in place, so modifiers
   and materials survive. Alternatively, *Apply as Plain Mesh* detaches the object from Iteron for sculpting or editing.

**C — later phases** (the core is designed with these in mind from the start):
* Ray-marched live preview while dragging sliders.
* Keyframed parameters rebuilt per frame.
* Hybrid formulas: a chain of steps, Mandelbulb3D style.
* 3D flames / IFS as point clouds.
* Opening Fractalchemy `.fa` / `.fa3d` scenes and `.fafrag` / Fragmentarium `.frag` files (§7).
* Volumes.

### 1.4 What Iteron deliberately does not do

* No new windows or editors, no pop-up dialogs (apart from Blender's own file browser for *Import*),
  no Properties-editor panels and no redo-panel clutter. Operators hide their *Adjust Last Operation* panel when it
  would only duplicate the sidebar.
* No custom exporters, renderers, decimators, smoothers or undo system. Blender already has all of them.
* It never edits a mesh the user is editing: live rebuilds pause in Edit Mode and the status line says why.

## 2. How it works

```
 formula definition (Python, once)
   ├─► schema ──► generated PropertyGroup ──► sidebar widgets, presets, tooltips, keyframes
   ├─► traced ──► GLSL kernel + params UBO ──► gpu_eval: offscreen slabs ──┐
   └─► numpy   ──► cpu_eval (chunked, worker thread) ───────────────────────┤
                                                                            ▼
        Region (auto-fit) ─► distance grid ─► surface nets (quads) ─► colour/normals at vertices
                                                                            ▼
                                        bpy Mesh (foreach_set) + attributes + Iteron material
```

### 2.1 A formula, defined once

```python
@formula("Mandelbulb", family="Bulbs", kind=ESCAPE, distance=LOG_DE, bounds=1.3,
         description="The classic White–Nylander power bulb",
         params=(Float("power", 8.0, 2.0, 16.0, "Exponent of the triplex power"),),
         presets={"Classic": {}, "Quad": {"power": 4.0}, "Tentacles": {"power": 3.0, "iterations": 20}})
def mandelbulb(z, dr, c, p):
    r = length(z)
    dr = pow(r, p.power - 1.0) * p.power * dr + 1.0
    return tpow(z, p.power, r) + c, dr
```

* **`ops`**: a small vocabulary of ~40 GLSL-named functions (`vec3`, `dot`, `length`, `clamp`, `abs`, `mod`, `mix`,
  `select`, `pow`, `atan2`, `acos`, `rotate`, `tpow`, `sd_box`, …). Each one dispatches on its argument type:
  * **numpy arrays** (the CPU path, float64, vectorised over a chunk of points) → calls numpy.
  * **symbolic values** (the GPU path) → records an SSA expression. `trace.py` then emits one GLSL function from the
    record. Python control flow over constants (static params, fixed fold counts) simply unrolls. Point-dependent
    choices use `select(cond, a, b)`, and using a symbolic bool in a Python `if` raises a clear error at load time.
* **One loop primitive**, `iterate(count, state, body, until=…)`, covers the runtime-bounded iteration:
  * **numpy:** masked lanes.
  * **GLSL:** a `for` up to a maximum with a `break`.

  The runners (escape-time with the log or linear distance estimate, direct DE, orbit-trap colouring) are themselves
  written against `ops`, so they are traced too. Apart from the probe `main`, there is no hand-written GLSL to keep in
  step with numpy.
* **Params**: `Float`, `Int`, `Bool`, `Vec3`, `Enum`, each with a default, a soft range, a description, a group and a
  `static` flag. Runtime params go into a generated **uniform buffer** struct; `static` ones are baked into the shader,
  which is recompiled and cached on change. A UBO is used rather than push constants because push-constant space is
  small on Metal and Vulkan.
* **Shared options come from the kind, not from each formula.** Every `ESCAPE` formula automatically gets
  *Iterations*, *Bailout* and *Julia + C*, and every formula gets the colour modes. A "Juliabulb" is therefore the
  Mandelbulb with *Julia* on, not a second copy.
* A **parity test** evaluates every formula on both paths at random points and compares, allowing for float32 vs
  float64.

### 2.2 Evaluating the field

* **GPU (`gpu_eval/`)**: `GPUShaderCreateInfo` → shader, `GPUOffScreen(..., format='RGBA32F')`. The grid is drawn as
  slabs (k z-slices side by side per draw), the technique Fractalchemy's probe uses (`fragments/gl/mesh.py`). Red holds
  the distance and green the trap value. Slabs are drawn in time-sliced ticks on the main thread (`bpy.app.timers`),
  because the `gpu` module is main-thread only.
* **CPU (`cpu_eval.py`)**: the numpy kernel over chunks of points in a worker thread (numpy releases the GIL), with
  results handed back to the main thread by a timer. It is used for `blender -b`, *Compute device: CPU*, and as the
  automatic fallback if the shader fails to compile (the reason goes to the status line).
* **Auto-fit**: a 32³ pass shrinks the box to where the field crosses the surface, plus a margin.

### 2.3 Meshing

* `surface_nets.py` is ported from Fractalchemy `solid/isosurface.py` (its `resolve_ambiguities` too). The changes:
  * **No scipy.**
  * **Quads kept as quads.**
  * **Colour sampled exactly.** Instead of interpolating a colour grid, the trap is evaluated **at the vertex
    positions** with the same kernel — one extra small pass.
* The surface is the level `DE = offset × voxel` (Fractalchemy's *threshold in voxels*, since many estimators never go
  negative inside).
* **Normals**:
  * *Smooth*: Blender's smooth shading.
  * *Field gradient*: central differences of the DE at each vertex, set as custom normals. This is faithful to the
    fractal rather than to the voxel steps.
* **Clean-up is left to Blender**: Weld, Decimate, Smooth and Remesh modifiers, none of it re-implemented.
* **Memory guard**: dense grids are capped by the memory limit (512³ float32 ≈ 0.5 GB). Sparse block meshing for larger
  resolutions is a later phase (Fractalchemy already does this in `fragments/mesh.py`).

### 2.4 Writing into Blender

* `mesh_write.py` clears the object's existing mesh datablock and refills it with `foreach_set` on vertices, loops and
  polygons. It never uses `from_pydata`, which is too slow for millions of faces. Filling in place keeps materials,
  modifiers and linked duplicates intact.
* **Attributes**:
  * `iteron_trap` (float, point domain): feeds the material.
  * `Col` (colour, point domain): the ramp baked in, so glTF / PLY exports carry colour.
* **Material**: one per object, created on add: *Attribute (`iteron_trap`) → Color Ramp → Principled BSDF*. The Color
  section draws that ramp node's widget, so the palette lives in one place.
* **Staleness**: a hash of the parameters (and of the formula version) is stored on the mesh. `undo_post`, `load_post`
  and property updates compare it and schedule a rebuild only when it differs. Opening a `.blend` never recomputes
  anything.

### 2.5 Jobs and responsiveness

* One `Scheduler` runs a queue of jobs: the active object first, and for the same object a newer request replaces an
  older one (Fractalchemy's supersede rule).
* A job is a generator of steps: fit → sample slabs → surface nets → vertex pass → write. The scheduler advances it from
  a timer with a ~30 ms budget per tick, and CPU-heavy steps run in a worker thread. Progress is shown in the header bar
  and the status bar. `Esc` or *Cancel* ends it, and a cancelled job leaves the previous mesh untouched.
* Property `update=` callbacks only *schedule*, with a debounce delay from Preferences. They never compute inline.
* Jobs refer to objects by name plus a pointer check and drop silently if the object is deleted mid-build.

### 2.6 Properties from the schema

* At register time, `props.py` builds one `PropertyGroup` class per formula from its schema (`type(...)` with generated
  annotations: subtype, soft min/max, description, `update=`). `IteronSettings` (a `PointerProperty` on `Object`) holds
  the formula choice, the shared settings, and one pointer per formula group.
* Because each formula keeps its own values, switching formulas and back restores them.
* Parameters are real typed properties, so keyframes, drivers, copy-to-selected, *Reset to Default* and Python access
  (`obj.iteron.mandelbulb.power`) all work.
* The panel draws any formula with one function, `draw_params(layout, group, schema)`.

## 3. Architecture

The repository root keeps `LICENSE`, `README.md` (now headed by the logo), `branding/` and `sample_source/`. The
add-on is the `iteron/` folder, which is what gets zipped. Each file targets under ~250 lines, with 400 as a hard limit: a file that grows past it
gets split.

└─ tools/
   ├─ run_blender_tests.py      the suites inside a real Blender (or `python -m pytest tests` with the bpy module)
   ├─ check_install.py          installs the built zip through Blender's extension installer and exercises it
   ├─ render_gallery.py         docs/images/ — every formula's default rendered with EEVEE

**Dependency direction:** `core` ← `formulas` / `interop` ← `gpu_eval` / `bridge` ← `jobs` ← `ops` ← `ui`. No layer imports a
layer to its right. `core`, `formulas` and `interop` never import `bpy`, so they run and test without Blender (and could back a
command-line tool later).

## 4. Engineering rules (DRY and small files)

1. **One source of truth per fact.**
   * A formula's parameters, ranges, defaults, descriptions and presets exist only in its `@formula` call.
   * Shared per-kind options (iterations, bailout, Julia, colour modes) exist only in `runners.py` / `formula.py`.
   * The GLSL and numpy paths come from the same function.
2. **One code path per job.** Preview and final builds are the same pipeline with a different resolution. GPU and CPU
   differ only in the evaluator object passed in.
3. **One drawer.** `ui/draw.py` draws every parameter from the schema. There is no per-formula UI code.
4. **One registration helper.** Every module exposes `classes = (...)` (plus an optional `register_extra()`), and
   `__init__.py` registers the modules in order and unregisters them in reverse.
5. **Reuse Blender before writing code**:
   * exporters, modifiers (clean-up), the colour ramp, undo, keyframes;
   * the preset menu pattern for user presets;
   * `layout.panel()` for folding sections instead of a class per sub-panel.
6. **Small files**, ~250 lines as a target and 400 as a hard limit. Functions do one thing, with type hints and
   docstrings (Fractalchemy's style). An `# SPDX-License-Identifier: MIT` header goes on every file.
7. **Extension hygiene**: relative imports only, no `sys.path` edits, no writes into the add-on folder, and
   `__package__` as the preferences id.

## 7. Opening Fractalchemy files

There is one import operator, reached from *File ▸ Import ▸ Fractalchemy* or the quick-start's *Open Fractalchemy
File…*. It picks a reader by file extension. The readers in `interop/` never import `bpy`. Options such as *which
flames* and *add camera / lights* appear in the file browser's own side panel, so there's no extra window.

| File | What it holds | What it becomes in Blender | Phase |
|---|---|---|---|
| `.fa` | JSON: one or more flames (transforms, variations, 3D camera, palette, colouring) | One Iteron *flame* object per chosen flame (point cloud, or mesh through the same surface nets). The palette becomes the colour ramp; the flame's 3D camera can become a Blender camera. | 4 |
| `.fa3d` | A `.fa` flame plus per-transform materials, up to 8 lights, environment and mesh settings | The flame object plus: one Principled material per transform (diffuse, specular, shininess mapped across); distant lights → Sun lamps (their camera-relative altitude/azimuth turned into world rotations); point lights → Point lamps; environment → World colour and strength; camera → Blender camera; mesh settings → the Mesh section. Instancers / holons follow later with Geometry Nodes. | 4 |
| `.fafrag` / `.frag` | GLSL distance estimator, annotated uniforms, `#preset`s (and in `.fafrag`, Fractalchemy's JSON metadata block) | An Iteron *fragment* object: parameters from the annotations, presets from the `#preset` blocks, meshed by the same GPU sampler. Optionally, the preset's `Eye / Target / Up / FOV` becomes a Blender camera. | 5 |

**Flames.** Iteron evaluates the variations it implements, starting with Fractalchemy's natively written builtins.
Any variation a file uses that Iteron lacks is named in the status line and skipped, as Fractalchemy does.

Fractalchemy's large C-dialect formula library can't be bundled because it is GPL-derived. Iteron *can*, though,
compile formulas from the user's own Fractalchemy formula folders at run time, by porting `formulas/lang/` (the
author's MIT code). Deciding on that is a Phase 4 task.

**Fragments** are GLSL, so they run only on the GPU: the tracer can't turn them into numpy, and there is no background
mode. The status line says so.
* **Includes.** Fragments usually `#include` FragM's files (`DE-Raytracer.frag`, `MathUtils.frag`, …), which are GPL
  and can't ship with Iteron. Iteron ships its own small MIT **shims**:
  * The raytracer includes reduce to what a distance estimator needs (`orbitTrap`, the `baseColor` hook, the raytracer
    uniforms as inert values).
  * `MathUtils` is re-implemented.

  Any other include is looked up beside the file, then in the **include folders** set in Preferences (for example
  the user's Fractalchemy or FragM installation). A missing include is reported by name.
* **Parameters.** A fragment's uniforms aren't known when the add-on registers, so they live in a generic typed
  collection on the object (`iteron.fragment.params`). The same `draw_params()` draws them, from a schema built from
  the annotations, so one drawer serves built-in formulas and fragments alike. They stay keyframeable
  (`iteron.fragment.params["Power"].value`).
* **Self-contained `.blend`.** The fragment's source is kept in the `.blend` as a Text datablock, so the file opens
  anywhere; *Reload from Disk* re-reads the original.
* **Live preview.** Phase 3's ray-marched preview works for fragments too, since it's the same GLSL path.

Writing Fractalchemy files back out isn't planned; it can be added if it's wanted.

## 9. Phases

Each phase ends with something installable and usable.

### Phase 0 — spikes ✅ done
Each answers a question the design depends on:
1. **GPU sampling**: a traced-by-hand Mandelbulb kernel through `GPUShaderCreateInfo` + an `RGBA32F` offscreen + slab
   packing. Check it compiles on OpenGL, Metal and Vulkan, and measure time and read-back cost for 96³ and 384³.
   Measure `texture.read()` → numpy conversion in particular, since it may set the slab size.
2. **Tracer**: the `ops` dispatch plus SSA emission on the Mandelbulb and Mandelbox. Confirm the GLSL is readable and
   that numpy and GPU agree.
3. **Mesh write**: surface nets → `foreach_set` for 0.2 M, 1 M and 5 M quads. Time it and check undo memory.
4. **Background mode**: is `gpu` usable under `blender -b`? This decides when the CPU path is the default.

**Answers** (measured against the `bpy` 4.2.0 and 5.0.1 modules, OpenGL on Mesa llvmpipe — a software rasteriser):
1. **GPU sampling works.** `GPUShaderCreateInfo` with `typedef_source` plus a `uniform_buf` compiles in about 3 ms,
   and a 96³ grid draws and reads back in 0.06–0.2 s, even in software. Two traps:
   * **Read-back:** the shaped `Buffer` that `read_color` returns exposes *reversed strides* to numpy, so read into
     a flat `Buffer` instead (then `np.asarray` is instant).
   * **GPU state:** set it explicitly (depth test, blend, culling, viewport), because whatever was drawn last
     silently swallows the draw.
   Metal and Vulkan could not be tested here.
2. **The tracer works.** It produces readable SSA GLSL, and every formula and preset agrees with numpy: 27 parity
   cases on llvmpipe, plus 8 more through Blender's own `gpu` module.
3. **Mesh writes are fast.** 1.8 M quads are written with `foreach_set` in 1.2–1.8 s. Surface nets, rewritten
   sparse, take 3.8 s at 384³ (the dense port took 48 s) with a 0.9 GB peak.
4. **Not in background by default.** `gpu` refuses to draw in `blender -b` until something creates a GPU context
   (an EEVEE render does; the tests use that). Background builds therefore use the CPU.

### Phase 1 — MVP: add, tweak, build, render ✅ done
* Scaffold: the manifest, `__init__` registration loop, preferences, and the build script (which copies the branding
  icons into `iteron/icons/`).
* `core` in full: params, formula registry, ops, vec, trace, runners, glsl, cpu_eval, grid, surface_nets.
* `formulas`: the 8 in §6 with presets.
* `gpu_eval` sampler with CPU fallback, and the `jobs` scheduler with debounce, supersede, cancel and progress.
* `bridge`: generated properties, mesh write (quads, `iteron_trap`, `Col`), default material, staleness handlers.
* UI: the `Shift+A` submenu with the Iteron icon, and the sidebar (header with the icon; Shape, Region, Mesh, Color).
  The quick-start state shows the logo and a plain formula menu; the thumbnail gallery comes in Phase 2.
* Operators: add, rebuild, build final, cancel, apply preset, apply as plain mesh.
* Tests: core pytest suite, Blender smoke tests, GPU↔CPU parity.

**Done when:**
* The zip installs on Blender 4.2 LTS and on 5.x, the main development target (Windows, macOS, Linux).
* `Shift+A` adds a fractal with a visible preview in about a second.
* Dragging a slider updates the 96³ preview without blocking the UI.
* *Build Final* at 384³ completes with progress and can be cancelled.
* Undo/redo, save/reopen and linked duplicates behave.
* A glTF export carries colours.
* No file exceeds 400 lines, and `core` imports no `bpy`.

**Outcome.** Everything above is built and tested. There are 68 bpy-free tests and 45 in-Blender tests, run on
Blender 4.2.0 and 5.0.1. The zip installs, enables, disables and re-enables through Blender's own extension
installer (`tools/check_install.py`). Every formula and preset was rendered and inspected (`tools/render_gallery.py`).
The largest file is 295 lines.

**Changes from the design**, each for a reason found while building:
* **GPU work runs in a viewport draw callback, not in timers.** The `gpu` module is only guaranteed a context while
  Blender draws, on every backend. The timer requests a redraw, the draw callback draws the next slab, and the timer
  writes the mesh (data is never changed while drawing). If no 3D viewport draws for 1.5 s, the build moves to the
  CPU.
* **Colours come from the sampled grid.** The kernel writes distance plus three colour channels in the same pass;
  vertices take them by trilinear interpolation. That means one shader and no second pass. Distance is stored as
  float32 and colours as float16, which halves memory.
* **All three colour channels are stored on the mesh** (`iteron_trap`, `iteron_iterations`, `iteron_radius`), so
  switching the colour mode is instant, with no rebuild. The baked `Col` attribute is refreshed after builds, on
  mode changes and (debounced) on ramp edits.
* **Background mode never queues builds.** Nothing ticks there, so parameter edits in `blender -b` don't start a
  build; scripts call `rebuild` / `build_final`, which run synchronously.
* **Builds overlap by rule.** A running *preview* finishes while you keep dragging, so the viewport keeps updating;
  a running *final* build is cancelled by any change.
* **Defaults were chosen from renders.** Mandelbox defaults to scale 2, because -1.5 meshes as a near-solid block.
  Amazing Surf starts tilted, because with no rotation it is a flat sheet. Octahedral *Twisted* was dust, so it was
  replaced.

**Found in the source material.** Fractalchemy's `3D - Mosely Snowflake.frag` centres its cells on odd integers
(`mod(p*s, 2) - 1`), so the cuts land half a cell off. Its corner cut's face also coincides with the cube's face,
which leaves a phantom skin where the corners should be missing (a ray-marcher hits it too). Iteron's version fixes
both, and tests check it against exact Mosely membership. Fractalchemy's fragment could take the same two fixes.

**Not verified here** (no display or GPU in this environment):
* the live UI — how the sidebar looks, and how dragging a slider feels;
* the Metal and Vulkan backends;
* Windows and macOS.

A first manual pass on Blender 5.x should cover these.

### Phase 2 — detail, polish and breadth ✅ done
Planned:
* A thumbnail gallery in the quick-start and formula menu.
* User presets (save / delete per formula). Reading and writing files outside the add-on needs the manifest's `files`
  permission.
* *Field gradient* normals, and a cut plane (slice the fractal open).
* The next batch of formulas from §6.
* A memory estimate shown before *Build Final*, and a clearer first-run hint.

Added at your request: **make the fine detail visible.** The Phase 1 Mandelbox looked chunky even as a final build.

**What was wrong** (measured against reference images ray-marched straight from each formula's estimator):
* **The main cause was the level, not the resolution.** Distance estimators underestimate — along a view ray the
  Mandelbox's reads about ¼ of the true distance, the bulbs' about ½. "Half a voxel of *estimated* distance" therefore
  put the Mandelbox's surface about two voxels out, which filled every groove. Doubling the resolution cost 8× the
  faces (13.3 M) and didn't help, because the shell inflated with it.
* **Vertices sat on a linear guess** between two samples, so ridges melted.
* **Normals came from the facets**, so nothing finer than a face showed.

**What was built** (`core/refine.py`, `core/blocks.py`, `core/simplify.py`):
* **Calibrated level.** Each build measures how much the estimator underestimates *on its own surface*: pilot
  patches at full resolution, placed on near-surface points from the coarse pass, are re-levelled until the median
  |∇d| settles. It settles at about 0.25 for the Mandelbox, 0.35 for the bulbs and 0.95 for the sponges; the first
  refinement pass then re-measures it on the whole surface. The Surface Offset is now in voxels of *true* distance,
  and each formula brings a recommended one: 1.25 for the Mandelbox, whose sub-voxel detail would otherwise alias
  into speckle, and 0.5 for the sponges, whose holes must stay open.
* **Refinement.** Newton steps move every vertex onto the level set. Each uses a 5-point stencil (the point plus a
  tetrahedron: exact value, exact gradient), and two steps put 95 % of vertices within 0.01 voxel of the surface
  (it was 0.1 – 0.4). The last stencil also gives the **field normals** (Blender custom normals) and the exact vertex
  colours.
* **Sparse blocks.** A build is meshed 160³ block by block, with only the blocks the surface can reach sampled, so
  memory follows the surface and resolutions up to 1024 work. Blocks carry an 8-voxel halo, matching the 8
  ambiguity-resolution passes, so they agree exactly at the seams: a test checks that a many-block build equals a
  one-block build. Surface assembly numbers cubes with a dense mask when the grid is small enough (6× faster than
  sorting).
* **Simplification** (optional, Build Final only; default 0.1 voxel). Adaptive vertex clustering on the voxel octree:
  a cell merges when its vertices' tangent planes agree (the dual-contouring QEF), and clusters that would make a
  non-manifold edge are split again. It keeps the mesh closed and manifold. It removes about 55 % of the Menger's
  faces but only about 10 – 25 % of the Mandelbox's and the bulbs' — their surfaces are detailed at every scale, so
  their detail *is* their face count.
* **Face and memory estimate** for Build Final, scaled from the current mesh (faces ≈ resolution^2.5, exponent
  measured at 2.2 – 2.7).
* **Frame View** (Region): the region becomes the viewport's pivot at its current zoom, so a close-up spends the
  whole resolution on what is seen.

**Result.** At 256³ the whole Mandelbox shows the reference's holes, arcs and rings, cleanly. The Mandelbulb and
Menger match their references to the resolution limit.

**Also done:**
* **The cut plane:** a global `Cut` group every formula gets, shown under Region.
* **User presets:** JSON files in the extension's user folder; the manifest declares `files`.
* **Thumbnails:** EEVEE-rendered and transparent. They fill the quick-start's icon gallery and the Add menu, and the
  README gallery is composed from them (`tools/render_thumbnails.py`, `tools/compose_gallery.py`).
* **Five new formulas:** Folding Int Pow, Lambdabulb (with a running derivative in place of the fragment's
  finite differences), ABoxMod1, Jerusalem Cube and Koch Tetrahedron. There are 13 in all.

**Dropped from this batch:** the Sphere-Inversion IFS and the Kleinian Limit Set. Both are infinite tilings whose
structure is finer than any practical voxel, so as meshes they are noise or cut slabs. They suit the Phase 3
ray-marched preview better. Translating the Kleinian did expose a tracer bug, now fixed and tested: loop state that
is passed through unchanged was overwritten before being read in GLSL.

**Performance notes.**
* A 384³ surface-nets pass takes about 4 s.
* Writing 1.1 M faces with custom normals into Blender takes about 3 s on the main thread.
* CPU builds are about 10× slower than GPU ones, mostly in kernel evaluation.

## 11. Risks

| Risk | Mitigation |
|---|---|
| `gpu` module limits: main thread only, backend differences, read-back speed | Phase 0 spike 1; time-sliced slabs; the CPU path as automatic fallback |
| Tracer coverage: a formula needs a construct the tracer lacks | Grow `ops` deliberately. A formula may ship a hand-written GLSL override, but then the parity test must cover it. |
| Large meshes inflate undo memory and `.blend` size | Preview stays small by default; the final build is explicit; the status line shows the face count |
| float32 on the GPU loses detail in deep regions | The Region section meshes a detail at high resolution; the CPU path is float64 when needed |
| Blender API drift between 4.2 and newer releases | A thin `bridge/` layer; CI-style smoke tests on 4.2 LTS and 5.x |
| Fragments using features the shims or Blender's shader pipeline lack (textures, buffer shaders, doubles, legacy GLSL corners) | Scope Phase 5 to distance estimators; report unsupported features by name; the Collection examples are the acceptance set |
